## 回到已有 P0 流程（本增量实机状态 NOT_RUN）

由能访问本地 Mac 和隔离容器的执行者完成以下顺序，保留每项命令、退出码和原始证据。
不扫描或上传真实凭证、OA 数据、生产恢复目录或整个工作区。安全 CI 的 Python 矩阵
不改变 dsh-sim 自己要求的 Python >=3.12 或其既有验证依赖锁。

### 1. 只读盘点与隔离

记录宿主/容器架构、DSH 版本、两仓完整 SHA、工作区是否脏、安装副本来源、项目和数据库
对应关系。使用新 worktree/恢复目标/测试数据目录，不覆盖日常实例、已有数据库或日志。
宿主上的脚本和容器内源码都必须对应固定的 dsh-sim SHA；不只更新宿主脚本。
旧密钥撤销、hooks 实装与 CI 回归分别记录；没有操作证明就保持 NOT_VERIFIED。

### 2. 先测部署，不碰日常容器

在候选 Assets 执行上述安全入口。在 dsh-sim 宿主源码根先执行无 Docker 的隔离回归：

```bash
python3 -m unittest discover -s tests/deployment -p test_transport_failure.py -v
```

然后在已经配置好软件和映射的**专用、无业务运行中的一次性验收容器**执行原入口：

```bash
bash deployment/local-acceptance/test-run-local.sh "$ACCEPTANCE_CONTAINER"
```

注意原脚本会发信号并清理它创建的目录，run-local.sh 还会使用固定进程模式定位残留；
更换 DATA_DIR 并不能隔离同容器中的其他实例。禁止指向日常容器。
Docker 未就绪、查询 UNKNOWN、停止超时或代码身份不一致时立即阻断，不继续启动第二份作业。

### 3. 宿主加载、真实 MCP 和工程核心回归

### 4. 五个真实求解场景与四阶段模型链

沿用配套仓现有入口，每场都用新目录，实际命令例如（在已准备的求解环境中）：

```bash
.venv-openfoam/bin/python -m dsh_sim.validation.openfoam \
  --local-validation --case baseline --output /new/location/channel-baseline
```

分别执行 baseline、transfer、solver-failure、cancel、timeout；它们仍是开发回归，
不称为新的盲测。取消/超时需真实 solver 日志、终态和进程组退出证明。
随后自然语言 plan → prepare → 人工授权 → execute → review；人工按钮只授权不提交，
授权后核查 runs=0，首次提交由 AGENT runner 经 submit_runs 完成，保存实际资源 ID 和摘要。
验证结果/冻结证据搬迁后能独立校验，篡改副本一个字节应拒绝。旧报告只作历史参考。

执行状态、数值状态、适用性与工程批准分别记录；DRAFT、TBD、INSUFFICIENT、UNCONFIRMED
不得升级成工程 ACCEPT。Worker 重启自动接管仍未实现，停止 UNKNOWN 时不可重复提交。
同模板未见参数仅在入口和实现冻结后由独立验收方给出；用来修复后就转为回归案例。
