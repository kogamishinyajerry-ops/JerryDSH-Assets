# 原型支线配方（eng-idea-to-ship 参考）

原型＝**回答一个问题的一次性代码**。问题决定形状。两条分支产出的东西差别很大，选错分支浪费整个原型：问题真含糊且用户够不着时，按周围代码默认（后端模块→逻辑；页面/组件→UI）并在原型顶部声明这个假设。

## 分支 A：逻辑原型（"这个状态模型手感对吗？"）

单文件、自包含 HTML（**可分享 demo**），让任何人按按钮驱动状态模型。用于业务逻辑、状态转换、数据形状——纸上看着合理、推过真实用例才觉不对的东西。一个文件零安装，可以递给非开发者（设计/PM/领域专家）亲手感受模型，所以它讲领域语言不讲代码语言。

做法：

1. **写下问题**：编码前把"在原型什么状态模型、回答什么问题"写成一段，放在 demo 顶部可见处（不只是注释）——答错问题的逻辑原型是纯浪费。
2. **逻辑隔离进可移植模块**：真正回答问题的代码放一个 `<script>` 块的纯小模块里（reducer `(state, action) => state` / 显式状态机 / 一组纯函数 / 方法面清晰的类——按*问题*选形状，不按接线方便选）。保持纯：不碰 DOM、按钮 handler 不伸进去。页面调它，反向无流。这样答案出来后，验证过的模块能整体抬进真代码库——页面是一次性的，这个模块不是。
3. **造 HTML**：无框架无打包无服务器，全内联，双击即开、邮件可发。每个标签用**领域语言**（按钮和状态读起来像业务不像 reducer）。
4. 每次动作后打印/渲染完整相关状态，让用户看见什么变了。

## 分支 B：UI 原型（"它该长什么样？"）

同一路由上生成**多套激进不同的 UI 变体**，`?variant=` URL 参数 + 悬浮底栏切换。用户浏览器里翻牌，选一套（或各偷一点），其余扔掉。

- **子形状 A（强烈优先）：现有页面的改造。** 路由已存在，变体渲染在同一路由、由 `?variant=` 门控，数据获取/参数/鉴权全保留，只换渲染。原型要嵌的页面"自然该长在某个现有页面里"也算 A。贴着真 app 才好评判：真 header、真侧栏、真数据密度。
- **子形状 B（兜底）：新页面。** 只用于真的没有现有页面可嵌的东西。按项目已有路由约定建**一次性路由**，命名让人一眼看出是原型。选 B 前先自查：真的没有页面能嵌吗？空路由藏起 populated 页面会暴露的设计问题。

## 两分支共享规则

1. **从第一天起就是一次性的，且明确标记。** 位置靠近真用途（上下文清晰），命名让路人看出是原型。
2. **跑起来零思考**：一条任务命令或双击。
3. **默认不持久化**：状态在内存。持久化是原型*要查*的东西不是依赖。
4. **跳过打磨**：不测试、不超必要的错误处理、不抽象——要快学。
5. **暴露状态**：每次动作后展示完整相关状态。
6. **完成时捕获**：验证过的决策折回真代码；原型本身作为**一手来源**提交到 `prototype/<name>` 分支（不进 main），实现 issue 上留指针；答案（结论+解决了哪个问题）记进 issue 或 commit。main 只留验证过的决策。
