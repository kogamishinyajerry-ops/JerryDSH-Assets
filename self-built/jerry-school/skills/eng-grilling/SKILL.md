# 需求拷问（Grilling）

对用户穷追不舍地访谈，直到达成共享理解。把要讨论的东西建模为一棵**设计树（design tree）**：每个决策是一个节点，每个决策分出依赖它的子决策。

按**轮次（rounds）**推进这棵树。**前沿（frontier）**＝所有前置决策已定的决策：即*现在*就能问、不用猜未听过的答案的问题。一轮把整个前沿问完：每个问题编号、给出你的推荐答案，然后等用户回答，再进入下一轮。

## 每轮格式

```
❓ **Q1** - **<问题标题>**：<问题正文，可以多段、可含选项>

➡️ <你的推荐答案>

---

❓ **Q2** - **<问题标题>**：<问题正文>

➡️ <你的推荐答案>
```

在 DSH 中优先用 `ask_user_question` 工具提交一轮问题（每题一个稳定 id，选项附推荐标注）；不适合结构化的开放题用上述文本格式。

## 两条铁律

1. **找事实是你的活，永远不是用户的。** 前沿问题需要环境事实（文件系统、工具、依赖行为）时，自己去查——派一个只读子代理或直接读代码，绝不问用户任何你自己能查到的东西。不要因此阻塞：进行中的探索就是一个"未定前置"，只有它下游的问题等它回报，前沿其余问题照常现在问。
2. **做决策是用户的。** 每个决策摆给用户并等待。

## 轮次如何推进

用户的每个回答都会重塑设计树：已定决策把前沿向外推，解锁原本依赖它们的问题。每轮结束重算前沿再问下一轮。答案依赖本轮仍未定的问题的，属于*更晚*的轮次，不属本轮。

## 结束条件

前沿为空：设计树每个分支都已走过，没有任何东西被默默假设。**在用户确认达成共享理解之前不得动手实现。**结束前用 ≤10 行复述已定决策清单请用户确认。
