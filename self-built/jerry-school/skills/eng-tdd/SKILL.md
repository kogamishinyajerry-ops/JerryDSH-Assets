# 测试驱动开发（TDD）

TDD 就是 red → green 循环。本技能是让这个循环产出*值得保留的测试*的守则：什么是好测试、测试放在哪、反模式、循环的规则。每一节在**每个循环前后都要对照**，不是收尾时才看。

探索代码库时先读 `CONTEXT.md`（若存在），让测试名与接口词汇跟项目领域语言一致，并尊重所在区域的 ADR。测试写法示例与 mock 边界见 [reference/tests-and-mocking.md](reference/tests-and-mocking.md)。

## 什么是好测试

测试通过**公共接口**验证行为，而不是实现细节。实现可以整个换掉，测试不应该跟着变。好测试读起来像规格说明："用户可以用有效购物车结账"——它告诉你存在什么能力，且因为不关心内部结构而能在重构后存活。

## Seam：测试住在哪

**Seam** 是你测试所处的公共边界：不伸进内部就能观察行为的接口。测试只住在 seam 上，永不针对内部。

**只在预先约定的 seam 上测试。** 写任何测试之前，先写下要测的 seam 清单并与用户确认；未经确认的 seam 上一条测试都不写。你不可能测所有东西——事先约定 seam，就是把测试火力落在关键路径和复杂逻辑上而不是每个边角。

要问："公共接口是什么？我们应该测哪些 seam？"

当接口本身的形状还在争论（模块该多深、seam 放哪、接口该暴露什么）时，加载 `eng-codebase-design` 技能取词汇——它是 module/interface/depth/seam/adapter/leverage/locality 的唯一词源，是查阅的参考不是要跑的会话。

## 三个反模式

- **实现耦合**：mock 内部协作方、测私有方法、走旁路验证（绕过接口直接查数据库）。识别标志：重构后行为没变但测试挂了。
- **同义反复（tautological）**：断言用实现同样的方式重算期望值（`expect(add(a,b)).toBe(a+b)`），构造上必过、永远无法与实现分歧。期望值必须来自独立真值：已知字面量、手工算例、规格。
- **水平切片**：先写完所有测试再写所有实现。批量测试验证的是*想象中的*行为——测的是东西的形状而非用户面对的行为，且在理解实现之前就锁死了测试结构。改用**垂直切片**：一个测试 → 一个实现 → 重复，每个测试都是响应上一轮所学的**曳光弹（tracer bullet）**。

## 循环规则

- **先红后绿。** 先写失败测试，再写恰好让它通过的代码。不预判未来的测试、不加投机功能。
- **一次一片。** 每循环一个 seam、一个测试、一个最小实现。
- **重构不属于这个循环。** 它属于审查阶段（见 `eng-code-review`），不属于 red → green 实现循环。
