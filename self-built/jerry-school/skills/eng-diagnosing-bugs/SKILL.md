# 诊断 Bug（Diagnosing Bugs）

给疑难 bug 的纪律。只有在显式说明理由时才能跳过阶段。

探索代码库时先读 `CONTEXT.md`（若存在）建立相关模块的心智模型，并查所在区域的 ADR。

## 脱敏（Redact）

本技能要展示命令、输出与捕获物。**先脱敏一切密钥**：原位写 `<REDACTED>`。回路基于环境变量构建，凭证留在环境里而不是展示物里。捕获物带 auth 头：只引用携带信号的那几行。脱敏后不够诊断就明说，向用户要。

## 阶段 1：造一个反馈回路

**这一步就是本技能的全部，其余都是机械操作。** 有一个针对*这个 bug* 会变红的紧信号，你就能找到原因——二分、假设检验、插桩都只是消费它。没有它，盯着代码看多久都没用。

在这里下不成比例的功夫。**激进一点，有创意一点，拒绝放弃。** 十种回路的构造方式（失败测试、curl 脚本、回放 trace、fuzz、bisect harness、HITL 脚本……）见 [reference/loop-recipes.md](reference/loop-recipes.md)。

**收紧回路。** 把回路当产品：能更快吗（缓存初始化、跳过无关步骤）？信号能更锐利吗（断言具体症状而不是"没崩"）？能更确定吗（钉死时间、固定随机种子、隔离文件系统、冻结网络）？30 秒的闪烁回路 barely 好过没有；2 秒的确定回路是调试超能力。

**非确定性 bug**：目标不是干净复现而是**更高的复现率**。循环触发 100 次、并行化、加压力、缩时间窗、注入 sleep。50% 闪的 bug 可调试，1% 的不可调试——持续抬高比率直到可调试。

**真造不出回路时**：停下并明说。列出试过的东西。向用户要：(a) 能复现的环境访问权，(b) 脱敏的捕获物（HAR、日志、core dump、带时间戳的录屏），或 (c) 加临时生产插桩的许可。**没有回路不进入假设阶段。**

**完成判据：一条紧的、能变红的回路。** 你能说出**一条命令**（脚本路径、测试调用、curl）——你已经跑过至少一次（展示调用与输出，脱敏），且它：

- [ ] **能变红**：驱动真实 bug 代码路径并断言**用户描述的确切症状**，不是"没报错"——它必须能*抓住这个 bug*
- [ ] **确定**：每次运行同一判决（闪烁 bug：按上文钉住高复现率）
- [ ] **快**：秒级，不是分钟级
- [ ] **agent 可跑**：无人值守可运行，人只在回路里时走 HITL 脚本

发现自己在这条命令存在之前就开始读代码建理论——**停：跳 straight to 假设正是本技能要防的失败。没有能红的命令，没有阶段 2。**

## 阶段 2：复现 + 最小化

跑回路，看它变红。确认：

- [ ] 回路产生的是**用户描述的**失败模式，不是恰好邻近的另一个失败。抓错 bug = 修错 bug。
- [ ] 多次运行可复现（非确定性 bug：够高的复现率）。
- [ ] 已捕获确切症状（错误信息、错误输出、耗时），后续阶段才能验证修复真的解决它。

**最小化。** 变红后把复现缩到**仍会变红的最小场景**：输入、调用方、配置、数据、步骤**一次删一个**，每删一次重跑回路，只留下对失败 load-bearing 的部分。为什么值得：最小复现收窄阶段 3 的假设空间（可怀疑的活动部件更少），并成为阶段 5 干净的回归测试。**每个残留元素都 load-bearing**（删任何一个回路都变绿）才算完成。没有复现并最小化，不往下走。

## 阶段 3：假设

测试任何假设之前先生成 **3–5 个排序假设**。单假设生成会锚死在第一个貌似合理的想法上。

每个假设必须**可证伪**：陈述它做的预测。

> 格式："如果 <X> 是原因，那么 <改 Y> 会让 bug 消失 / <改 Z> 会让它更糟。"

说不出预测的假设是感觉（vibe）：丢弃或锐化它。**测之前把排序列表给用户看**——他们常有瞬间重排的领域知识（"我们刚对 #3 部署了变更"），或知道哪些已排除。便宜的检查点，大省时间。用户 AFK 就按自己的排序继续，不阻塞。

## 阶段 4：插桩

每个探针必须对应阶段 3 的一个具体预测。**一次只改一个变量。**

工具优先级：1) 调试器/REPL（一个断点顶十条日志）；2) 区分假设的边界处的定向日志；3) 永不"全打日志再 grep"。

**每条调试日志打唯一前缀标签**，如 `[DEBUG-a4f2]`——收尾清理变成一次 grep。没标签的日志会活下来，打了标签的会死。

**性能分支。** 性能回归时日志通常是错的工具：先建基线测量（计时 harness、`performance.now()`、profiler、query plan），再二分。先测量，后修复。

## 阶段 5：修复 + 回归测试

**先写回归测试再修**——但仅当存在**正确的 seam**。正确的 seam 是测试以真实 bug 模式在调用现场发生的方式锻炼它的 seam。若唯一可用 seam 太浅（bug 需要多调用方而测试只有单调用方；单测复现不了触发链），在那里的回归测试给的是假信心。

**正确的 seam 不存在，这本身就是发现。** 记下来：代码库架构在阻止这个 bug 被锁死。标记给下一阶段（架构改进）。

有正确 seam 时：1) 把最小复现转成该 seam 上的失败测试；2) 看它失败；3) 施加修复；4) 看它通过；5) 对原始（未最小化）场景重跑阶段 1 回路。

## 阶段 6：清理

宣布完成前必须：

- [ ] 原始复现不再复现（重跑阶段 1 回路）
- [ ] 回归测试通过（或文档记录了 seam 缺失）
- [ ] 所有 `[DEBUG-...]` 插桩已移除（grep 前缀）
- [ ] 一次性原型已删除（或移到明确标记的调试位置）
- [ ] 胜出的假设写进 commit/PR message，让下一个调试者学到
